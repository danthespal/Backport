# Backport Studio findings

The single record of research, investigations, problems and solutions that are not part of the engine documentation. README.md keeps the engineering, verification and reference-project history. This file keeps what was learned from games, consoles and diagnostics.

Consolidated on 12 October 2026, before `tmp/` and the investigation folders in `work/` were deleted. Part 1 covers 11–12 October. Part 2 is the earlier work archive (`work/CONFIRMED_FINDINGS.md`, 10 October); its verification records and data tables were condensed on 14 October.

**Evidence standard.** Console observations, static binary facts and desktop test results are kept apart. A static import check or a passing desktop test is not a console compatibility result. Unless stated otherwise, console results come from the user's standard PS5 on FW 13.60, not from a physical FW 4.xx console.

**Surviving inputs.** The following remain in `work/`: the test fixtures (`*_elf`), `agc-4.03-patch/` (the `patch_agc.py` tool and ELFs that reproduce the shipped AGC patch) and `fakelib-backups/` (unpatched original `libSceAgc` for sets 4 and 4.03). Every other `tmp/…` or `work/…` path named here or in README is a former location. Its contents were deleted, and hashes identify files but cannot restore them.

# Part 1 — 11–12 October 2026

## 1. PPSA32935 Dynasty Warriors 3 Complete Edition Remastered: FW 4 build crashes, then saves fail

### 1.1 Launch crash: SDK-4 AGC workaround flags (fixed in the store)

- **Symptom.** The complete FW 4.00 cook on FW 13.60 showed a black screen, then crashed with `0xa0d0c006 GPU_FAULT_BAD_COMMAND_ASYNC`. The preceding packet error was `GPU Bad packet error: Bad opcode … opcode 0x00000000`. No CPU RIP was available (an asynchronous GPU fault). Complete 7.00 and 9.60 cooks of the same game worked.
- **Where the code comes from (static, 16 October).** `0xa0d0c006` is `SCE_KERNEL_EXCEPTION_GPU_FAULT_BAD_COMMAND_ASYNC`, one of the kernel's `0xa0d0c0xx` asynchronous GPU-fault exception codes. No user-space module in the 12.70 or 13.60 dumps (AGC, AgcDriver, libkernel) contains the constant or the "Bad packet" text. Only SceShellCore holds it, in a code→name table that the crash reporter uses (12.70 file offset `0x8bb21e`). Some games embed the same names, for example the Yotei eboot. The fault is raised by the kernel GPU driver when the command processor rejects a PM4 packet. In this case the packet had opcode 0, so the eboot's command buffer layout did not match what AGC wrote. That points at a user-side cause, not a kernel one.
- **Ruled out by console swaps.** Replacing the FW 4 AGC + AgcDriver, then AGC + AgcDriver + AMPR, with the working 9.60 files left the packet history and the fault unchanged. Psml was absent from every failing event's module list. The 7.00 cook shares the Psml-init skip, the Trinity stub, the memory adapter and the Wait32/Wait64 adapters, so those alone cannot explain a 4.00-only failure.
- **Mechanism (static, Sony AGC J03828141 / J03950001).** At init, AGC calls `sceKernelGetProsperoCompiledSdkVersion` (`GGeRJk1XdWc`), `getpid`, `sceKernelGetAppInfo` and `sceKernelTitleWorkaroundIsEnabled` with selectors `0x52`/`0x53`/`0x70`. It then keeps flag bits 0/1 **only when the process reports SDK major 4** (`cmp edx,0x04000000; cmovne eax,esi`). Bits 0/1 change AcquireMem packet emission. Bit 0 also grows `sceAgcDcbAcquireMemGetSize`/`sceAgcAcbAcquireMemGetSize` from 32 to 64 bytes, and one path emits an extra `0xc0065800` packet. Swapping the library alone cannot bypass this, because the eboot still reports SDK 4.

  | 4.00 AGC evidence | ELF VA |
  | --- | --- |
  | Compiled-SDK query | `0x8a71` |
  | SDK-major-4 compare / conditional clear | `0x8c1d` / `0x8c23` |
  | Flags store / variable | `0x8a89` / `0x45f9c` |
  | DCB / ACB AcquireMem flag reads | `0x3888`,`0x3896` / `0x222`,`0x22c` |
  | DCB / ACB AcquireMem size functions | `0xd680` / `0xd990` |

  The 9.60 AGC has the same logic at `0x8c0d`/`0x8c13`, variable `0x49f9c`.
- **Fix.** At VA `0x8c23` (file offset `0xcc23`), `0f 45 c6` (`cmovne eax,esi`) becomes `89 f0 90` (`mov eax,esi; nop`). This selects the SDK 7/9 calculation, clears bits 0/1 and keeps bit 2. It changes no SDK field or dependency, and it behaves differently only when a process reports SDK major 4. The fix is shipped in `fakelibs/4/libSceAgc.sprx` (SHA-256 `07a995b3…`) and `fakelibs/4.03/libSceAgc.sprx` (`73611ebe…`, built with unwrap → patch → sign, which reproduces the set-4 file byte for byte). Details are in `fakelibs/README.md`.
- **Status.** The set-4 file booted on FW 13.60, and a fresh Studio FW 4 build of PPSA32935 boots, saves and reloads there (Automatic Pro, Save mount + Save preparation compatibility). The 4.03 file is not console-tested, and neither file has been run on a physical FW 4.xx console. Whether those flags are *needed* on real FW 4 is unknown.
- **Repeat result.** Bisect test I (below) hit the same GPU crash later, using the backport's own unpatched AGC (`eace8ac1…`, identical to the old store file). That confirms the cause.

### 1.2 Never mix modules from different target cooks

Whole-eboot swaps between the 4.00 and 9.60 outputs gave `PRX_SCE_MODULE_LOAD_ERROR` in both directions. A hybrid (9.60 eboot/libc/graphics trio, the rest from 4.00) logged three `load_prx failed 0x63` and then a SIGSEGV at runtime RIP `0x49e21fc` (`mov rax,[rax+0xc]`, RAX 0). EOS/KITT modules were missing from its module list. An eboot-only SDK 12 build also failed: `0xa0020102` "Lack of a .prx file in /app0/sce_module". A process at SDK 12 rejects SDK 4 `sce_module` libraries. **Mixed-SDK module sets do not load.** Diagnostic tests must change a whole coherent set, or vary one rule inside one cook.

### 1.3 Save failures: DirNameSearch `0x809f8007` (resolved, console state)

- **Symptom.** The booting FW 4 build saved with CE-107098-5, or its saves did not reload. The kernel log showed every `sceSaveDataDirNameSearch` (api_id 6) failing with `ExecResult 0x809f8007`. The game's search callers turn any nonzero return into "0 saves" (e.g. VA `0x5f6a201..216`), and its commit/unmount wrapper at `0x5f78600` discards both returns. So a "Saving" message proves nothing.
- **What `0x809f8007` is.** From decrypted SceShellCore FW 12.70 and 4.03, decompiled in Ghidra: ShellCore GetResult (12.70 VA `0x1950f0`) → result copy (`0x1a3540`) returns `0x809f8007` only when the stored result is larger than the caller's buffer. It is not a database, file or missing-save error. The search handler (`0x11c070`) always stores `0x11308` bytes, and the console's own libSceSaveData.native passes a fixed `0x11308` buffer (4.03, 9.60, 10.01, 12.00, 12.70). The game supplies only the `0xc0`-byte condition and never chooses the size, so backport files cannot set either size. Per-app service flags (ctx+`0x134`) come from the reported compiledSdkVer and param ATTRIBUTE2 bit 17, not from param.json `sdkVersion`/`requiredSystemSoftwareVersion`. In the FW 9.60 client, `0x809f8007` is the IPMI reply status; client-side validators produce only `0x809f8004`/`8009`.
- **Bisect (all on FW 13.60, original-signed control + one change each).** AMPR + PlayGo fakelibs: pass. A, backport libc (heap flag 0x8000 adapter, SyncOnAddress adapters, cxa redirect, 4 stubs): pass. B, backport eboot: pass. C, backport eossdk: pass. D, all five 4.00 fakelibs: pass. E, `requiredSystemSoftwareVersion` 0x04: pass. F, A+B+C+D+E: pass. G, F + `ampr_emu.index` + `k9.psp`: pass. I, the real 4.00 eboot/prx/sce_module at process SDK 4: search passes (and the GPU crash from 1.1 appears). Probe v3 had shown that every argument variant (capacity 1024/32/1, explicit title/dirName) failed identically while in the failing state.
- **Conclusion.** No Studio file or rule causes the search failure. The full SDK 12 overlay failed, yet G passed with identical files and identical param content, so the failure came from console/title state at the time. All failing runs predate the switch to the original game folder, and the failing histories show unidentified APIs 68/71/116 before the search. The fresh Studio build no longer shows the error. On a real FW 4 console the client/service pair is Sony's matched pair, so this failure is not expected there. Still open: decrypted 13.60 ShellCore + libSceSaveData.native would confirm the 13.60 sizes. Test H (backport param + forced re-registration) was never run.

### 1.4 SaveData rules learned

- **`save_mount_compat` must never apply to a process reporting a high SDK.** Under SDK 12 the service rejects create mounts with systemBlocks 0 ("You cannot create save data with systemBlocks set to 0", `0x809f8004`) and needs −1. Under SDK 4 it accepts 0, and the library substitutes the default (logged `systemBlocks=96`). This is consistent with the rule's `below 5.00` limit.
- **PPSA32935 call sites.** Mount3 at VA `0x5f7858e` receives a struct at `rbp-0x80`. Its systemBlocks (`rbp-0x68`) is set to −1 at `0x5f7857b` (the earlier "96" was a service-side log value). The same caller zero-initialises the SaveDataPrepare mode, so the prepare mode-2→1 adapter is a no-op for this game. The save/create function at `0x5f6b520` uses Mount3 mode `0x20`.
- **Normal for this game:** `SaveInfoData` mount `0x809f8022` (not found), and GameStatusData read `0x809f8022` before the first save.
- **The working 9.60 build is not a save baseline.** It showed "Saving" but then "Failed to load data" after reopening.

### 1.5 Console/diagnostic facts from this investigation

- **Native eboot text must be X-only.** A diagnostic that added a `PF_R|PF_X` load segment was rejected: `_exec_self_imgact:1437: R+X segment in native program /app0/eboot.bin`, `0x80aa001a`/errno 8. Diagnostic code must go into the zero padding after the existing X-only text, with strings in the read-only data padding, keeping all 14 segment entries and their permissions.
- **Unsigned plain ELFs do not load.** The "decrypted" original (plain `7f454c46` eboot/sce_module) failed with `sceSblAuthMgrAuthHeader … error 46`, then `Load error (libc.prx)`. A control run of an original game needs every module fake-signed unchanged; the round trip differs only at ELF header `0x3c–0x3f`.
- **AMPR logging does not trace ordinary file I/O.** `AMPR_FILE_WRAPPER_LOGF` is defined as `((void)0)` in `fakelib_source/libSceAmpr/include/ampr_emu_log.h:66`. The supplied AMPR 0.3.6.6 log (64/64 hooks installed) contained no `/savedata` activity. Use explicit SaveData/file-I/O tracing instead. The `rc=0x80020010` AIO init message alone does not mean a broken I/O engine.
- **ShadowMountPlus** has no SaveData hooks. It mounted the game's own fakelib directly into the sandbox common/lib; no global SaveData replacement was involved.
- **BackPork** 6xx/7xx `libSceSaveData.native.bps` only lowers module SDK fields (plus 6xx relocations). It contains no search fix.
- **Same console, other title.** PPSA24003 (original, compiledSdkVer `0x11000040`) runs DirNameSearch without error. The original PPSA32935 calls it twice (count, then fetch); the backport made only one call.

### 1.6 Open issue: generic `sceKernelSyncOnAddressWait` adapter contract

The current derived rule (`proven: false`) assumes a 32-bit expected value and `_umtx_op` operation 11 (WAIT_UINT), taken from an emulator signature. Decrypted Sony FW 7.01 and 9.60 binaries keep RSI as 64 bits, use operation 2 with a tagged address and a custom sixth argument, convert timeouts and handle return values. In PPSA32935's libc, generic Wait is called at `0x118ee5` on an 8-byte state (`lock cmpxchg qword`). The 4.00 cave at `0x6eb46` has `mov edx,esi` and selects op 11, while the 7.00 cook keeps the native Wait/Wake pair. That call passes expected value 1 and a null timeout, so truncation does not explain any observed failure, and libc passed bisect A. **This is a real ABI discrepancy with no observed failure.** A "wide wait" libc (op 2, 64-bit, 17 bytes) was built but never tested, and it still does not reproduce Sony's timeout, queue/tag or return-value behaviour.

## 2. PPSA38510 The Walking Dead: Streets of Survival (Unity IL2CPP): startup SIGSEGV at RIP 0 (open)

- **Symptom.** The game crashed immediately on FW 8.60, and on a 10.20 Pro per the later log: SIGSEGV, RIP 0, fault address 0. The eboot base is `0x400000`. The backtrace in ELF terms: `0x77e216`, `0xd21cf7`, `0xd2536a`, `0xd25d85`, `0xd25ab9`, `0x162b755`, `0x16352be`, `0xaf`. The game is Unity PS5_13_00, original SDK `0x13000035`, cooked to `0x04000031`.
- **Mechanism (static + registers).** Constructor `0xcb0510` calls slot `0x22e7ac8` at `0xcb071d`. That slot is zero-initialised and is written only at `0x163397b`, with `il2cpp_api_lookup_symbol("il2cpp_set_find_plugin_callback")`. The runtime module list lacks **`Il2CppUserAssemblies.prx`**. Startup `0x163529b` → IL2CPP init `0x16318f0`, which loads `%s/Modules/Il2CppUserAssemblies.prx` at `0x16319c0`. A false return is recorded, and execution continues into `0x1622730`, which reaches the unset callback. This is the same failure pattern as Crow Country (Part 2 §1), but here the cause of the load failure is unknown: file open, loader rejection or another init failure.
- **Ruled out.** A missing null guard (the factory at `0x77e1d0` checks its callback; this superseded the first reading). Unsupported flags (RSI `0x34` is the startup argument size; ECX/R8 are 0). The static import report for all 12 modules against the exact 8.60 reference has missing = 0 and unknown = 0. The IL2CPP module differs from the original by 5 metadata bytes only.
- **Diagnostic, never console-tested.** An eboot with `48 8d` → `0f 0b` (UD2) at file offset `0x16359fc` (ELF VA `0x16319fc`, reached only by the negative-load branch at `0x16319ca`). If the load fails it raises SIGILL at runtime RIP `0x1a319fc`, with the loader error in R14's low 32 bits. Signed SHA-256 `9819c2df…`. The crash log is also the regression sample for `ps5backport crash-log`.

## 4. Psml model filename experiment (not promoted)

The FW 4-set Psml (SHA-256 `72855f03…`) reads `/app0/k9.psp` (string at VA `0x5c039`). Four `lea` references at `0xe0d2`, `0xe0d9`, `0xeb85` and `0xeb8c` were redirected to a new string, `/app0/KPN9_v070.psp`, at VA `0x4ffe0` (file `0x53fe0`) in the zero tail of the executable segment. That is 27 ELF bytes, with no segment changes; the result is `4106180918…`, and the model hashes are identical (`22ffbf06…`). It passed static and cook checks but was never console-tested with PSSR, so it was not promoted. The store keeps `k9.psp`. A useful test needs a game known to use PSSR on a Pro.

Why the name is `k9.psp` (2026-10-13): both sites are `snprintf(buf, 0x100, fmt, root, name)` and then an open. Sony's code passes `fmt = "/%s/common/psml_package/%s"` (still at file `0x600db`) and `name = "KPN9_v070.psp"`. That name is absent from the patched file. Its 14-byte slot at VA `0x5c039` (13 characters + NUL) now holds `"/app0/k9.psp\0\0"`, and both `lea`s point there; the path has no `%`, so the format arguments are ignored. An in-place name can have at most 7 characters (`/app0/` + 7 + NUL = 14), so `/app0/KN9.psp` fits exactly, with no code changes. The 9.60 Psml (`cfe210a3…`) has the same layout: same VA, the same two NULs and the same `lea` sites. The full original name needs the relocation described above.

**The first experiment was flawed (2026-10-13):** its string sat in the text segment, which is execute-only (`p_flags = 1`, X only; PS5 enforces XOM). `snprintf` reading it would fault. **Built instead: variant `psml_kpn9`** (option `psml_kpn9`, sets `4` and `9.60`). The string `/app0/KPN9_v070.psp\0` is placed in read-only rodata at VA `0x5c033..0x5c046`, ending where the old slot ended; `0x5c047` is referenced and stays unchanged. It overwrites the tail of the fatal message at `0x5bfe4` (`...shared resources memory blocks.`, printed only before a `ud2`; only its start is referenced), which now ends at `memory`. The four `lea`s are repointed to `0x5c033`, and no `/app0/k9.psp` remains. Unwrap → patch → sign, and the result unwraps back to the patched ELF. 9.60 `sign(unwrap)` reproduces the store file byte for byte; for set 4 only a 32-byte digest field in the SELF header differs, as for the set-4 AGC. Cook checks (UFC 6 dump at FW 9.60, GT7 1.71 `default` at FW 4): with the option the output has the variant Psml and `KPN9_v070.psp` but no `k9.psp`; every other file is identical. Not console-tested.

### 6c. Audit: rules that rely on the target firmware lacking the function (2026-10-13)

- **Principle:** a cook targets the *lowest* firmware, but the same eboot runs on every newer console. A `kind: stub` rule only pre-fills the GOT. Wherever the console's firmware exports the function, the loader binds the real one, and the real one runs with the game's arguments and the lowered SDK stamp (4.00). `plt_stub`, `adapter`, `swap` and `redirect` patch the PLT or rename the import, so they hold on every firmware. Risk class: a `stub` function whose accepted arguments widen in a later firmware (Set3DLatency: 0–1 on 6.00–9.60, 2 from 10.01). SDK-gated differences are harmless, because the stamp makes every firmware take the SDK 4.00 path.
- **First firmware exporting each rule's function** (`firmware_db`, 43 lists; 7.00/11.20/12.60/13.60 dumps encrypted or missing): GetOperationMode 11.00; IsTrinityMode/HasTrinityMode 7.01; GetAvailableCpumask 12.40; SyncOnAddressWait8/16 12.00; VRR peg/unpeg/status 5.02; LatencyControlWaitBeforeInput/LatencyMeasureSetStartPoint 7.01; AllowOutputResolutionWqhdDetection 6.00; Set3DLatency 6.00; AcmBatchJobPriority 10.01; SaveDataCancel 6.00; GetGameTrialsFlag 6.00; CommerceDialogOpen2 7.01; PadIsRemoteController 10.01; Http2 WebSocket/SetRequestNoContentLength 5.02; ShaderTranscode never; libc ThreadDtors/ForceTlsDestructor/ThreadAtexit 11.00; Hmd2 SetAllowPositionalReprojection 6.50; GetOutputStatusWithVrr 10.01; AgcGetIsTrinityMode 9.00. Every renamed-to or redirect target (`IWIBBdTHit4`, `04AjkP0jO9U`, `tsvEmnenz48`) is exported from 1.00 to 12.70 without gaps.

### 6d. Audit: adapters and renamed imports on every readable firmware (2026-10-13)

Goal: every known and optional rule works from FW 4.00 to 11.60 (the last fpkg firmware) and ideally 13.60. Readable: libraries 1.00–12.70 (not 4.30, 7.00, 11.20, 12.60, 13.60) and SceShellCore for 3.20, 4.03, 4.51, 5.02, 5.50, 6.02, 6.50, 7.01, 7.60, 7.61, 8.60, 9.00, 9.40, 9.60, 10.01, 11.00, 11.40, 11.60, 12.00, 12.20, 12.70. Principle: the cook stamps SDK 4.00, and every firmware must keep running genuine SDK 4.00 games, so a value a genuine SDK 4.00 game passes is accepted everywhere. Where a firmware-specific check exists, it was read.

- **`sceUserServiceGetGamePresets` (`size` capped at 0x28, below 11.00): no effect on any firmware.** libSceUserService dispatches through a function table (copied from a static table, entry `+0xc8`) to a client that does only NULL checks, then IPC method `0x30026` with the game's struct as an *output* buffer of fixed length: 0x28 on 1.00–6.50, 0x30 on 7.01–12.70 (4.30/7.00/11.20 encrypted; 12.60 pattern not matched). The `size` field is never read, so the cap is harmless but unnecessary. (Assumption: IPC output buffers are not sent to the server.)
- **`save_mount_compat` (`systemBlocks` −1 → 0, below 5.00): correct on 1.00–12.70.** libSceSaveData.native picks the create-mount validator by the process's compiled SDK. On 12.70, function `0x1de80` checks `≥ 0x12000000` → `0x8220`, `≥ 0x09000000` → `0x7f70`, `≥ 0x05000000` → `0x7cc0`, else `0x7a00`. Rules for create modes (`mountMode & 0x24`), all firmwares scanned: SDK < 5.00 → `systemBlocks` must be **0**; SDK 5.00–11.x → 0 or −1 (FW 5.x: `inc; cmp 1; ja`; FW 6.00+: `dec; cmp -2; jb`); SDK ≥ 12.00 (FW 12.00+ only) → −1/−2, and 0 is refused with the "systemBlocks set to 0" message. - **`save_prepare_compat` (`prepareMode` 2 → 1): correct on 3.20–12.70.** No client-side check (IPC method `0x65`). ShellCore 3.20–4.51 refuse mode > 1 (`cmp eax, 1; ja` → `0x809f8004`). The rule could get `below: 5.00`, but it is not needed for correctness.
- **`audio_port_compat` (main port 0xC00 → 0x800, gain attribute 0x30 → 0x20, PCM fold): correct on 1.00–12.70.** In the `_sceAudioOut2LoPortCreate` validator of every readable libSceAudioOut, all channel masks contain 8 (`0x106` = 1/2/8, `0x504` = 2/8/10, `0x1106` = 1/2/8/12), plus `cmp eax, 8` on 3.00–5.50 and 7.01–9.60, and the `(fmt & 0xb00) == 0x800` path on 12.x. - **`audio_speaker_compat`** only masks the result (`+4` mask, `+8` flags). The layout is ABI (8.60 writes the same offsets from its fixed tables), so it is the same on every firmware.
- **`sceKernelMapNamedFlexibleMemoryInternal` → `sceKernelMapFlexibleMemory` (`IWIBBdTHit4`), flags `&= ~0x8000`: safe on 1.00–12.70 for every sample libc.** From **7.01**, `MapFlexibleMemory` refuses flags with any bit of `0x88000` (`test ecx, 0x88000` → `0x80020016`); 1.00–6.50 have no check. All 15 sample libcs (SDK 9–13: Yōtei, GT7, BL4, BF6, Silksong, KCD2, UFC 6, Dying Light, AC, Beast, PPSA34008, Control, Hades II, PPSA03671) call it only with the constant `0x8000`, so after the adapter the flags are 0. A future libc passing `0x80000` would fail on 7.01+; hardening the mask to `0xfff77fff` would cover that.
- **SyncOnAddress Wait/Wait32/Wait64/Wake → `_umtx_op` (`04AjkP0jO9U`): the target is the same `mov rax, 0x1c6; syscall` stub on 3.00–12.70**, and the ops (0xb WAIT_UINT_PRIVATE, 2 WAIT, 3 WAKE) are kernel ABI. **Defect found (firmware-independent): timed waits.** Sony's 12.70 `sceKernelSyncOnAddressWait32/64` read `[rdx]` as a 32-bit **microsecond** count and convert it. Game libcs call Wait32/Wait64 with `rdx = &u32_us` on the timed path (Yōtei libc `0x112091`–`0x1120b4`: ms × 1000 into `[rbp-0x14]`, `lea rdx, [rbp-0x14]`; same in GT7, Control). The adapters pass that pointer to `_umtx_op` as `uaddr2` with `uaddr = 0`, which the kernel reads as a 16-byte `struct timespec`: `tv_sec` = µs | stack canary bits << 32, `tv_nsec` = more stack. In practice this is almost always EINVAL (nsec ≥ 10⁹), so the timed wait returns at once (possible busy loops), and occasionally a near-infinite wait. Untimed waits (`edx = 0`) are correct. Wait (`Hc4CaR6JBL0`) is only called untimed in the samples. Wake is correct. Related: §1.6 (generic Wait's 64-bit value and op mismatch). This is the timeout half, and it also affects the `proven` Wait32/Wait64 rules.
- **`_sceLibcInternalThreadAtexit` → the game libc's own `__cxa_atexit`**: local to the game, firmware-independent.
- **Fixed (2026-10-13, user decision): Wait32/Wait64/Wait timeout and the MapFlexibleMemory mask.**

### 6f. Research: an in-game "Debug" notification from a backport (2026-10-13; implemented 2026-10-13)

- **How ShadowMount+ shows its toasts:** from its own payload process, `sceKernelSendNotificationRequest(0, &req, sizeof req, 0)` with `notify_request_t { char unused[45]; char message[3075]; }` (`src/sm_log.c:24`, `include/sm_platform.h:62`). That simple request is what the console renders as the "Debug:" toast in the 8.60 screenshot. It raises "Backport applied to game: %s" when it mounts the fakelib folder (`sm_fakelib.c:1877`), and "Error in game %s:
%s" when its log monitor (`sm_mdbg.c`, 60 s window) sees a fatal-signal block or a line containing `[rtld] <pid> ERROR`. Neither path reads any text from the backport files.
- **The API:** `sceKernelSendNotificationRequest` (`zl7hupSO0C0`) is a libkernel export on all 43 `firmware_db` lists (1.00–12.70). Implementation (4.00 `0x1b320`, 12.70 `0x1c030`): a once-init opens `/dev/notification%d` (0, 1, 7, blocking and non-blocking), then `write(fd, req, size)`; first argument ≤ 8 selects the device. So it is a plain device write, no privileged syscall.
- **Game modules do not import it.** None of 18 sample libcs nor 6 sample eboots; `sceKernelDlsym` only in some eboots (not Yōtei); `sceKernelLoadStartModule` in most. The engine cannot add imports (only rename), so a call would have to be made without an import.
- **Raw syscalls work from app code:** ps5-payload-sdk `samples/install_app/eboot.c` is an installed app eboot that executes `syscall` from its own text (no libkernel). So a cave can do `open`(5) `"/dev/notification0"`, `write`(4) the 3120-byte request, `close`(6), with no import. **Correction (console test below): this holds only for payload/exploit processes, not `native_game` — a game issuing a raw `syscall` is killed by the kernel.**
- **Generic hook point:** every sample eboot (GT7, Silksong, KCD2, Yōtei, AC, Control) has the same SDK `_start` at `e_entry` (`push rbp; …; mov r14d, [rdi]; mov rbx, rsi`), and its text is X-only (`flags 0x1`). A cave reached by redirecting `e_entry` can save registers, build the request and the path on the stack with immediates (X-only text cannot be read, so no string constants in text), make the three syscalls, ignore their results (branch-free, so `PlaceChain` may split it), restore, and `jmp` to the original entry. Engine pieces needed: write `e_entry`, a `PlaceChain` tail `jmp rel32 <entry>` variant, an option in `data/fixes.json` built by C# (like `UnitySkuFallback`), and a GUI text/checkbox (mock-up first).
- **Unknown, console test needed:** whether `/dev/notification0` is reachable from a game's sandbox (ShadowMount and the SDK samples run as payload processes). Cheapest test: a diagnostic eboot with the `e_entry` cave on one sample.
- **Alternatives:** (1) ask ShadowMount+ to append a text from the backport folder (for example `backport_publication.json` or a `backport_notice.txt`) to its "Backport applied" toast; no game patching, but a third-party change. (2) klog line via syscall `0x259` (7, text, 0) as in the SDK `klog()` sample: lands in the kernel log and ShadowMount's `debug.log`, not a toast unless it imitates `[rtld] <pid> ERROR`, which abuses the error path.
- **Implemented (2026-10-13; reworked to route through the game's own libkernel imports after the console test below):** option `boot_notice` in `data/fixes.json` + `src/Ps5Backport.Core/BootNotice.cs`. Redirects `e_entry` (recognised by the SDK `_start` prologue `push rbp; mov rbp,rsp; push r15` + the `mov r14d,[rdi]; mov rbx,rsi` signature) into one contiguous cave that replicates the overwritten 6 bytes, saves the caller-saved registers, builds `/dev/notification0\0` and the 3120-byte request on the stack as immediates, zeroes it with `rep stosq`, optionally sleeps (default 8 s) via the game's imported `sceKernelUsleep`, then calls the game's imported `sceKernelOpen`/`sceKernelWrite`/`sceKernelClose` **through their PLT stubs** (so each syscall runs from libkernel's text, not the game's), and `jmp`s back to the real entry. Message from `BackportOptions.BootNoticeMessage` (GUI text box, CLI `--boot-notice`; delay `--boot-notice-delay`). Verified by `BootNoticeTests` (redirect, immediate-encoded message/path, PLT call targeting, delay emission, pipeline wiring).

- **Console test — FAILED: a raw `syscall` from a game is fatal (2026-10-13, PPSA26344 on FW 4.00 `PPR:04000031`, three runs).** The cave crashed at its first `syscall`. Kernel log `PPRBUG-22859: the process pid=126 directly issued a syscall 240 at 0x1be9082`, then fatal `SYSTEM_ILLEGAL_FUNCTION_CALL` (`0xa002030a`) at `rip=0x1be9082`, inside eboot text (`0x400000:0x1bec000`; the process runs `category=native_game`). The kernel kills any `native_game` process that executes `syscall` directly (outside libkernel's text); the nanosleep (240) was merely the first, and `open`(5)/`write`(4)/`close`(6) would crash identically. **Fix paths:** (a) call the game's own libc imports (`open`/`write`/`close`/`nanosleep`) through their PLT stubs so the syscall runs from libc.prx's sanctioned text — needs the game's dynamic-symbol table to resolve the libc NIDs → PLT addresses (not present in the 180 KB minidump); (b) jump into a `syscall; ret` gadget inside libkernel's text (needs libkernel base + gadget offset); (c) post the toast from a payload process instead (ShadowMount-style). ShadowMount avoids this entirely because it is a payload (`shadowmountplus.elf`), not a game.

- **Option 1 implemented and statically verified (2026-10-13, user-selected).** The cave now calls the eboot's own imported libkernel functions through their PLT entries — `sceKernelOpen` (`1G3lF1Gg1k8`), `sceKernelWrite` (`4wSze92BhLI`), `sceKernelClose` (`UK2Tl2DWUns`), and `sceKernelUsleep` (`1jfXLRVzisc`) for the delay — so each `syscall` runs inside libkernel's text. `BootNotice.Apply` resolves these NIDs at cook time via `Patching.PltEntry` and returns 0 (leaves the module unchanged) when any of open/write/close is missing. - **Extended 2026-10-15 (§6p):** console-confirmed by the user on every eboot-hosted cook. An eboot that does not import open/write/close (PPSA18154) now gets the notice in its bundled libc's initializer. A first attempt that used `sceKernelDlsym` failed on the console and was removed. ### 6k. `sceSaveDataCancel` after the default Mount3 rule: native call kept (2026-10-14)

Question: with `systemBlocks` forced to 0 by the default `sceSaveDataMount3` adapter, does the native `sceSaveDataCancel` on 6.00+ consoles (the `ret0` GOT pre-fill is live only below 6.00, where the export is absent) hurt a 4.00 cook?

- **Games (unwrapped original eboots, `callers` scan for `call rel32` to the import's PLT entry, then disassembly of the following code):** CONTROL PPSA34547 calls it at `0x374da7d` and `0x374fdee`; PPSA03671 at `0x3f91159`. **All three discard the result.** No other sample game imports the NID. *(Refined 2026-10-17 by the caller-result check, §6v: at `0x374da7d` and `0x3f91159` `eax` is overwritten before any read. - **Function boundaries come from unwind info, no symbols needed.** Both eboots have a `PT_GNU_EH_FRAME` segment with a standard `.eh_frame_hdr` (version 1, encodings `0x1b`/`0x03`/`0x3b` = pcrel sdata4 / udata4 / datarel sdata4 sorted table). FDE count: Control `work/CONTROL_elf/eboot.elf` 189,972; GT7 `work/NOT_BACKPORT_elf/eboot.elf` 156,935 (read in 47 ms; no overlapping ranges; largest function 121,719 bytes / 15,520 instructions / 200 basic blocks). Function size = the FDE's `pc_range` (encoding from the CIE's `zR` augmentation).
- **MSAGL layered layout is fast enough:** 33–163 ms per function, including GT7's largest.
- **GT7 4xx+/USA eboot vs the original (`work/GT7_root_elf` vs `work/NOT_BACKPORT_elf`), 47 changed bytes in total:** (1) one in-place patch at `0x83403a` in `sub_833f60`, `mov qword ptr [rdi+18h], -1` → `0`, a field of the `sceSaveDataMount3` argument block (the call at `0x834050`); (2) two stubs in int3 padding: `0x3d2` `xor eax,eax; ret` and `0x573` `mov dword [rdi],2; and dword [rsi],0; xor eax,eax; ret`; (3) six GOT slots repointed to those stubs: `sceKernelGetOperationMode` → `0x573`, and `sceVideoOutVrrPegToFixedRate`, `sceVideoOutVrrUnpegFromFixedRate`, `sceVideoOutAddVrrStatusFlagsPrivilege`, `sceVideoOutAddVrrActiveStatusEvent`, `sceKernelGetAvailableCpumask` → `0x3d2`; (4) the SDK version fields in the process param. Nothing else in `.text` changed and `.text` did not grow.
- **Studio's own GT7 FW 4 cook vs the original `default` eboot** (15 October): 5 stubs and 2 rewritten PLT entries, no in-place patch. The `sceSaveDataMount3` adapter is split over four int3 caves (`0xd6` → `0xe6` → `0x3d2` → `0x405`: `mov rax,[rdi+18h]; lea r11,[rax+1]; test r11,r11; cmove rax,r11; mov [rdi+18h],rax; jmp [Mount3@got]`, i.e. field +0x18 = -1 becomes 0, the same effect as GT7's in-place patch) and reached through its PLT entry; the caves sit between tiny functions (e.g. the 5-byte `sub_e0`). One-piece stubs match data/stubs.json: `ret0` (5 imports incl. `sceHmd2ReprojectionSetAllowPositionalReprojection`), `opmode_normal`, `ret:0xff` (`sceKernelGetAvailableCpumask`), `ret:0x8a810012` via the `scePsmlMfsrInit` PLT entry.
- **Switch tables** (15 October): indirect jumps in GT7 are mostly virtual calls (`jmp [reg+off]`, 5,672) and vtable tail calls (`jmp reg` after a load); compiler switches use clang's relative table, `lea base,[rip+table]` (in .rodata, often hoisted into a callee-saved register such as r15 at the function start) + `movsxd r,[base+idx*4]` + `add` + `jmp r`, guarded by `cmp idx,n; ja` (sometimes `jae`, or `sub; ja`). Recognising that form resolves 2,198 tables in 1,454 GT7 functions (max 697 cases; e.g. `sub_82260`: 76 cases onto 2 blocks) and 1,296 in 933 Control functions; 29 GT7 jumps that load a `movsxd` entry stay unresolved, mostly `lodsq`-based copy loops.
- **Import check** (15 October): GT7 `default` eboot on FW 4.00 (exact firmware_db list, its `sce_module/` and `fakelib/` as providers): 927 imports available, 148 provided, 60 data, 2 already patched, 32 missing, called by 29 functions (e.g. `sceKernelGetOperationMode` from 11.00, `sceAgcGetIsTrinityMode` from 9.00, the `scePsmlMfsr*` family from 10.01). After Studio's FW 4 cook only `sceHmd2ReprojectionSetParamWithBuffer` (libSceHmd2, from 5.02) stays missing, matching the cook report's "left unpatched by: GT7 1.71 FW4" line.
- **Call-site constants, decoded vs the probe's byte scan** (15 October): over 6,000 GT7 call sites (rdi/rsi of the first 400 PLT imports), the decoded per-block reading and `Imports.ArgumentConstants` agree on all 19 real constants and never contradict each other; the byte scan alone reports 84 more, all false positives (an immediate inside an earlier instruction's bytes, or a write before a previous call or jump: e.g. `mov edi, eax; call exit` read as 213, `__cxa_begin_catch(1107296254)`). The decoded reading finds nothing the byte scan misses. **Resolved the same day:** the requirements probe now reads decoded call sites (`Imports.ArgumentConstants`: the byte scan only picks the functions to decode). On the 14 sample games that import `scePadSetVibrationMode` the sites, constants and verdicts are unchanged (UFC 6 needed with 4 at 6/6 sites; AC, Silksong, Horizon, BF6, FC 27 applicable; Dying Light, KCD2, Yōtei, Hades II not applicable; Borderlands 4, Beast of Reincarnation, PPSA34008 applicable), so no sample verdict ever rested on a false positive.
- **Most of the code in three games has no unwind entry** (15 October): Borderlands 4 (79 % of its 113 MB code segment), Beast of Reincarnation (82 % of 106 MB) and PPSA34008 (85 % of 124 MB) have large code gaps between FDEs; GT7 and Control have none (< 0.01 MB). Their pad calls sit in such code, so the probe decodes a window ending at the site (from the last int3 padding up to 8 KB before it). The Code graph page now discovers functions there (README "Code graph page"): on GT7 with its unwind table removed, call targets alone find 43 % of the real starts at 98.5 % precision, RELATIVE-relocation code pointers 31 % at 100 %, 16-byte-aligned code after int3 padding 94.5 % at 98 %; together 98.5 % at 98.1 % (Control 99.3 % at 96.9 %). Borderlands 4 grows from 34,745 to 431,203 functions (396,458 discovered); its pad call is in the discovered `sub_2518630` (42 bytes, no direct callers, so reached through a pointer). With discovery, Borderlands 4 on FW 4.00 shows 269 unresolved imports called by 483 functions.
- **Where the rule patterns match the sample eboots** (15 October, `Detectors.Find` on each `default` eboot): Wwise 7.1.4 → 7.1, all three patterns once each in code: Borderlands 4, Crow Country (PPSA03671), Dying Light, Beast of Reincarnation, Control (e.g. `sub_3ca3160`+0x8c); Horizon CotM only the packed default. Frostbite 0x30c buffer: UFC 6 (`0xe4bec0`). audio_bed_71: Yōtei's two (`0x304077`, `0x34d4f7`). gpu_scratch `s_trap 1` in eboot data: 1 (Kena) to 422 (Crow Country), 164 in most. No match: BF6, KCD2, FC 27, Hades II. The Unity and Ubisoft recognisers match no sample eboot.
- **Code caves are at most 13 bytes** (15 October, `Patching.Caves` on the `default` eboots): the caves the engine uses are the int3 fill of 16-byte function alignment, so after the two guard bytes none holds more than 13 bytes. GT7: 38,736 caves, 257,911 usable bytes, extension room 6,356 bytes (99 blocks); Control: 35,566 / 224,555 / 8,324; Borderlands 4: 150,496 / 816,531 / 2,596; Hades II: 2,018 / 14,470 / 8,532. Every stub longer than 13 bytes is split into jump-joined pieces (like GT7's 4-piece Mount3 adapter), and code that must stay in one piece (contiguous adapters, the boot notice) can only go into the extension. Studio's GT7 FW 4 cook fills 8 caves with 67 bytes.
- **Strings and data the code reaches** (15 October, `CodeImage.DataAt` / `ScanCalls` on GT7's original eboot): code takes the address of 38,934 distinct strings with `lea` (only 13 of them UTF-16: the force-feedback device names such as `L"FSDeviceWheelCSW"`); many are assert paths from the build tree (`C:\pdi\src\gt7\maintenance\...`), class names and log messages, which makes functions findable by text. Pointers stored in data are not in the file: the slots are filled by `R_X86_64_RELATIVE` relocations (base + addend), so a pointer's target must be read from the RELA table, not the bytes. A naive UTF-16 test took 517 "strings" there, mostly halfword tables decoding as CJK; requiring three quarters ASCII leaves the 13 real ones.
- **Fakelib modules are ordinary clang modules** (15 October, `CodeImage` on fakelibs/4, 4.03, 7, 9.60 and GT7's shipped fakelib/): every one has a PT_GNU_EH_FRAME unwind table (libScePsml 1,220–1,303 functions, libSceAgc 342–343), and every GT7 eboot import of a fakelib library is an export at a function start, except in the 4.03 set: its libScePsml lacks the SDK 13 entry points `scePsmlMfsrCreateContext1300` (kLF7WtQ1-Dg) and `scePsmlMfsrGetDispatchMfsrPacket1300` (DDVUyPyYHTA), which GT7 imports (sets 4 and 9.60 have them). The 7.xx set ships `libSceSaveData.native.sprx` for the library that imports name `libSceSaveData_native`. In GT7's fakelib, `sceAgcInit_0090` (0x9990) compares its return address with a pair of addresses loaded from 0x46070 before tail-jumping to `sub_8a20`; what that check is for is not verified.
- **UFC 6 v1.004 → v1.005, function by function** (15 October, `VersionMatch.Compare` on `decrypted` and `dump`; the only sample game with two different builds, every other variant pair is one build): 471,373 → 471,544 functions; 471,078 paired, 470,380 of them identical code (439,926 moved), 698 changed, 466 new, 295 removed. No symbols to check against, so consistency instead: callees of paired functions map onto each other's callees 99.8–100 % in every pass, their strings agree 99.5–100 %, except the weakest pass (the only unmatched caller/callee left, 88 pairs: callees 97.9 %, strings 56.9 %), which the page marks "check it". Unique fingerprints alone pair 165k; the call graph and the address order between anchors pair the other 306k (many small functions have identical copies). Anchors must be the longest chain of pairs in address order: a greedy left-to-right walk let a few out-of-order pairs swallow regions above 0x5000000 and left 61k functions unmatched on each side. Sanity: GT7's original against its own backport pairs all 156,935 functions with themselves; the one changed is the patched `sub_833f60`.
- **Unverified oddity:** the *original* `sub_833f60` already contains `setae cl; xor ecx,ecx; nop; inc ecx` before `mov [rdi+20h],ecx`, which discards the `setae` result. That looks like an earlier patch rather than compiler output, so `NOT_BACKPORT_elf` may not be a clean dump. Not checked against the `default` SELF.

### 6p. Boot notification skipped on Tomb Raider IV-VI Remastered (PPSA18154): eboot without file-I/O imports (2026-10-15)

- **Symptom:** a FW 4.00 cook with `boot_notice` (`D:\PS5\BackportTests\PPSA18154 - Tomb Raider IV-VI Remastered\PPSA18154_backport_4.00`) showed no toast. The report listed the option but the `eboot.bin` section had no `pattern Boot notification` line: `BootNotice.Apply` returned 0 and nothing reported it (the probe said `console-choice`).
- **Cause:** the eboot (`C:/TRX2_builder/.../eboot.bin`, SDK 9.00, 227 imports) has the standard SDK `_start` at `e_entry` (`0x70`), but imports **none of** `sceKernelOpen`/`sceKernelWrite`/`sceKernelClose`, nor POSIX `open`/`_open`/`write`/`_write`/`close`/`_close`. The game code lives in `4/tomb4.prx`, `5/tomb5.prx`, `6/tomb6.prx`, which the eboot loads. Of the cave's functions it imports only `sceKernelUsleep`. It does import `sceKernelDlsym` (`LwG8g3niqwA`) and `sceKernelLoadStartModule` (also `fopen`, `fclose`, but not `fwrite`).
- **First fix (user-selected, 2026-10-15; part 2 superseded below because the lookup fails on the console):** (1) the probe now says `not-applicable` with the reason when no module can carry the notice (`no module has the SDK _start entry the notice hooks`, or `eboot.bin imports neither … nor sceKernelDlsym`). A cook with the option selected that applies it nowhere adds the warning `option Boot notification (Debug toast): not applied, <reason>`. (2) A function the eboot does not import is resolved at boot: `sceKernelDlsym(0x2001, "<name>", &slot)` through the eboot's own dlsym PLT entry, then `call [rsp+slot]`. `0x2001` is the libkernel handle `fakelib_source/libSceAmpr` already uses (`kKnownLibkernelHandle`). Lookups run **only for functions that are not imported**; imported ones keep their PLT call, so an eboot that has them gets no lookup. All lookups run before the first call; a non-zero result or a null address jumps straight to the register restore, so the notice is skipped and the game still starts. Stack frame 0xC60 → 0xC90 (16-byte name buffer at 0xC60, four 8-byte slots at 0xC70); call sites stay 16-aligned.
- **Static check on PPSA18154:** the cook now prints `pattern Boot notification (Debug toast) x1`. The cave at `0x1079be` performs three lookups (`sceKernelOpen`/`Write`/`Close`, handle `0x2001`) through `0x107090` = the `sceKernelDlsym` PLT entry (GOT `0x16f030`), then `sceKernelUsleep` through its PLT `0x106ed0` (GOT `0x16ef50`), then `call [rsp+0xc70/0xc78/0xc80]`. Every failure branch lands on `add rsp, 0xc90`, and the cave jumps back to `e_entry+6`.
- **Not verified:** that handle `0x2001` is libkernel in a `native_game` process on FW 4.00 (the Ampr fakelib relies on it, but this is the first eboot-level use) and the toast itself (the §6f sandbox question). Needs a tester run of a PPSA18154 cook.
- **Console result (user, 2026-10-15): the 13:41 re-cook (cave present, `pattern … x1`) still shows no toast.** No log was collected. The game starts.
- **Deeper static research (FW 4.00 libkernel and system libraries):**
  - **Our cave makes the same calls as Sony's.** `sceKernelSendNotificationRequest` (`0x1b320`) runs a once-init (`0x1b3b0`) that opens `/dev/notification%d` for devices 0, 1, 6 and 7 with POSIX `open(path, 1)` (O_WRONLY) and `open(path, 5)` (O_WRONLY | O_NONBLOCK). It then does `write(fd[dev][flags == 0], req, size)` and retries on EINTR. `sceKernelOpen` (`0x160b0`) is `open` plus errno → `0x8002xxxx`, and `sceKernelWrite` (`0x16080`) is `write` plus the same mapping. Path, flags, size and call sequence match the cave.
  - **Request formats used by firmware libraries that games load:** `libSceNet` (`0x163c0`) sends type 0, byte +0x2C = 0 and its text at +0x2D. The rest of its stack buffer is not cleared. This is ShadowMount's and our layout. `libSceSysmodule` (`0x18b3`, `0x3e1e`), `libSceHmd` (`0x111e4`) and `libSceVrTracker` (`0xeba43`) send **type `0x64`**, with -1 at +0xC and +0x10 (msgId and targetId), +0x28 = 0, +0x2C = 0 and the text at +0x2D. Sysmodule's text is `"Sysmodule:\n%s is loaded from the development machine system."`, a devkit warning. So Sony sends text toasts from inside game processes, but the only examples are devkit or debug paths. `libSceSysUtil` and `libSceNotification` use other layouts.
  - **Every PS5 reference that shows this toast is a payload, not a game:** ShadowMountPlus `sm_log.c`, ppr-patch `notify.c`, BackPork `main.c`, SDK `samples/notify_debug` and `hello_world`. Payloads run with escalated credentials outside the game jail. **No reference shows a toast from a `native_game` process on a retail console.** AnyPS5's emulator accepts only type 0 with +0x2C = 0 (no console evidence).
  - **The libkernel handle is not universal.** ps5-payload-sdk `crt/crt.c:98` and `crt/rtld_sprx.c:226,444` try handle `0x1` first and fall back to `0x2001`. `payload_terminate` treats a working `0x2001` as "inside a hijacked process", and the Ampr fakelib uses `0x2001` inside games. So `0x2001` is likely right for a game, but not proven. If it is wrong, every lookup fails and the cave skips **the 8 s delay too**, because the lookups run first. The game would then start without the delay.
  - **A diagnostic channel exists.** `sceKernelDebugOutText` (`9JYNqN6jAKI`, `0x266b0`) is `syscall 0x259(7, text, channel)` from libkernel's text. That is the same call as the SDK `klog()`, so it should reach the kernel log and ShadowMount's `debug.log`. A game's own `printf` does not (§6a). sceKernelDlsym is `syscall 0x24f`.
- **Failure points considered, in boot order:** (1) handle `0x2001` wrong, so no lookups succeed and there is no delay; (2) `open("/dev/notification0")` refused in the game jail (EPERM/ENOENT), with the delay but no toast; (3) the write is accepted but the shell ignores a type-0 request from a game process (only Sony's type-0x64 game-side format is shown on retail, or nothing from games is). Static analysis cannot decide between (2) and (3).
- **Console answers (user, 2026-10-15; `D:\PS5\debug.log`, ShadowMount+ 1.7-beta5fix1 on FW 13.60):** **the notice has appeared on every other game the user cooked** (all through eboot imports). So (2) and (3) are ruled out: a game process can open `/dev/notification0` and the shell shows the type-0 request. On PPSA18154 only ShadowMount's own "Backport applied" toast appeared. The log shows the 13:42 (pid 151) and 13:50 (pid 158) launches running until the user closed them, with no MDBG error and no crash. That is the cave's "lookup failed → skip" branch. **Cause: `sceKernelDlsym` on libkernel fails in a game process** (wrong handle or a kernel restriction on dlsym into system modules; PS4 jailbreaks patch such a restriction). Ampr's `0x2001` lookups prove nothing: `ampr_libkernel_hook.cpp` keeps its own imports as `AMPR_LIBKERNEL_SDK_FALLBACKS` and only overwrites them on success. The game itself uses `sceKernelDlsym` only on its own `.prx` handles from `sceKernelLoadStartModule` (`"run"`, `"exec"` at `0x6dbf`/`0x6dd7`).
- **Fix (2026-10-15): the dlsym route is removed; the bundled libc carries the notice instead.** Survey of every sample `default` eboot and `sce_module/libc.prx` (18 games) plus the D:\ test games. **18 of 20 eboots** import `sceKernelOpen`/`sceKernelWrite`/`sceKernelClose`. The exceptions are PPSA18154 (none) and Hades II PPSA36082 (no write). **All 18 bundled libcs** (module name `libc`, SDK 9.00–10.00) import `_open`/`_write`/`_close`/`_nanosleep` and begin `DT_INIT` (`0x10`) with `push rbp; mov rbp,rsp; push r15; push r14; push r13; push r12; push rbx; push rax`, in two register-allocation variants after that. The initializer is entered like a function and runs before the eboot's `_start`. `BootNotice.Assess` now picks **one** host per game: the eboot's `_start` when the eboot imports an open, a write and a close; otherwise the libc initializer. Each call uses the first imported alternative (`sceKernelOpen`/`_open`/`open`, and the same for write and close). The delay uses `sceKernelUsleep`/`usleep`, else `sceKernelNanosleep`/`_nanosleep`/`nanosleep` with `{delay, 0}` on the stack. `al` is cleared before open because POSIX `open` is variadic. The cave is otherwise the console-proven one (same request, same register save, `jmp` to hook + 6). Pipeline: the host is chosen before patching (`PatchContext.BootNoticeHost`); only that module is patched, and "not applied, <reason>" is reported when there is none.
- **Static check on PPSA18154 (scratch cook):** `eboot.bin` is untouched (`0x70` still `push rbp`). `sce_module/libc.prx` has `pattern Boot notification x1`: `DT_INIT 0x10` → `jmp 0x115bf2`, then `sceKernelNanosleep(&{8,0}, NULL)` (PLT `0x115b40`), `sceKernelOpen` (`0x115a00`), `_write` (`0x115750`), `sceKernelClose` (`0x1159e0`), then `jmp 0x16`. The probe says `console-choice … eboot.bin imports no open …, no write …, no close …, so the notice runs in sce_module/libc.prx's initializer`. **Console test pending** (re-cook PPSA18154). Expected: the toast about 8 s after launch, with no other change.

### 6q. `Il2cppUserAssemblies.prx` capitalisation: game spelling tried, then reversed, load path wins (2026-10-15)

- **Request (user):** some games need `Il2CppUserAssemblies.prx` and some `Il2cppUserAssemblies.prx`. Forcing the uppercase name leaves a duplicate when the game already has the lowercase file, so the game's or eboot's own spelling must be kept.
- **Evidence:** every Unity dump on disk has `Media/Modules/Il2cppUserAssemblies.prx` (lowercase c): V Rising PPSA16263 (root and `v3/`), Turbo Overkill PPSA19969, Valheim PPSA28824, Pathologic 3 PPSA30449, Silksong PPSA12544 (also its human 4xx+ backport), and Sons of Sparta PPSA28997. Each eboot holds both `%s/Modules/Il2CppUserAssemblies.prx` (Unity's load-path format) and `Il2cppUserAssemblies.prx`, which is the eboot's **`DT_NEEDED`** entry (next to `PS5Util.prx`, `libc.prx` …), plus import library `Il2cppUserAssemblies`. Studio's 15 October cooks of Turbo Overkill, Valheim and Pathologic 3 renamed the output to uppercase because the case rule skipped bare names. V Rising was left alone only because its two copies made the `%s` path ambiguous. Its uppercase file on disk (`Media/Modules` modified 16:20, after the 15:01 cook) is a manual rename, not Studio output.
- **Change:** a bare string that equals a game file's name exactly (ordinal) adds that file's own spelling as a reference. It never renames. With the `%s` path disagreeing, the result is the existing "conflicting file path casing … source filename preserved". Turbo Overkill re-cook: `Media/Modules/Il2cppUserAssemblies.prx` published, conflict warning listing both spellings.
- **Known trade-off (§8.1):** Crow Country's runtime opened `/app0/Media/Modules/Il2CppUserAssemblies.prx`, got ENOENT with the lowercase file, and booted after a manual rename. Its dump is no longer on disk, but its Unity eboot almost certainly has the same lowercase `DT_NEEDED`, so it would no longer be renamed. If a game fails with that ENOENT, rename the file on the console as before.
- **Reversed the same day (user decision, 2026-10-15): the load path wins.** The user cooked V Rising PPSA16263 and the game failed to boot looking for `Il2CppUserAssemblies.prx`, the same ENOENT as Crow Country. The `DT_NEEDED` bare name does not establish a location (it names no folder, and the module is loaded from `Media/Modules`, not `sce_module`), so bare names are no longer references at all; the §6q branch is removed. A second problem was specific to V Rising: its dump holds a second tree, `v3/` (`v3/game.bin` is byte-identical to `eboot.bin`; `v3/Media/Modules/Il2cppUserAssemblies.prx` is a different 405 MB build). The `%s/Modules/…` suffix matched both copies and was reported as "ambiguous file path casing", so nothing was renamed even under the old rule. Now a reference is ambiguous only when its matches differ **only by case**; a `%s/` suffix found in several folders applies its spelling to each copy. Real cook (FW 4): `file path casing corrected` for `Media/Modules/…` and `v3/Media/Modules/…`, no ambiguity or conflict warning, 44 files, 0 errors. Cost accepted by the user: an overlay on an installed game holds both spellings of the module. Test: `FilePathCaseTests.LoadPathRenamesEveryFolderCopy_AndBareNamesDoNotBlockIt`. **Console test pending** (V Rising re-cook).

### 6t. Research: a "guarded" fix kind (native function where it works, fallback elsewhere) (2026-10-16, design only)

Question: can one 4.00 cook call the real function on consoles that have it and fall back elsewhere, the way BF6 (README Part 16) and Horizon (Part 25) wrap imports by comparing the GOT with libkernel's unresolved-import trap?

- **The default `stub` kind already does this, through the loader. No runtime code is needed.** A `stub` pre-fills the GOT slot and keeps the `JUMP_SLOT` relocation. Two console facts cover both halves. (1) When the console lacks the export, the loader leaves the pre-filled slot alone, so the stub runs. GT7's FW 4 backport is built this way and works (README Part 11, "Confirmed working on console"). PPSA18154's 4.00 cook also boots on a physical 4.50 (§6s). (2) When the console has the export, the loader writes the native address over the pre-fill. Yōtei on 8.60 reached the native `sceAudioOut2Set3DLatency` and got `0x80268001` (§6b). So binding is eager where the NID resolves, and an unresolved slot is left as it is (and fails only if it is called while it still holds the lazy PLT stub). Both observations come from the ShadowMountPlus/kstuff environment, which is also where testers run.
- **The trap-compare wrapper is not worth adopting.** It needs a per-firmware trap address. Four firmwares are unconfirmed (4.30, 7.00, 11.20, 13.60), and Horizon's own wrapper compares with trap+2, which matches no firmware. It gives the same outcome as a pre-fill, with more ways to fail. A `sceKernelDlsym` lookup (`LwG8g3niqwA`, exported 4.00–13.60, imported by most sample eboots) would avoid the trap table, but it needs module handles and name strings for something the pre-fill already gets. Boot notification's `sceKernelDlsym(0x2001, …)` lookup also failed on a console (README "Boot notification: bundled-libc host").
- **Firmware-version guards are wrong for SDK-gated behaviour and not feasible anyway.** (a) The 4.00 stamp makes every console take its "SDK below N" paths (§6l, §6d). The always-active adapters (Mount3 below 5.00, `audio_port_compat`, GetGamePresets, `pad_vibration_compat`) are therefore needed on every firmware. A guard that switched them off on newer consoles would reintroduce the failures. (b) `sceKernelGetProsperoSystemSwVersion` (`aML18Z0J0t0`) and `sceKernelGetSystemSwVersion` (`Mv1zUObHvXI`) are exported from 4.00, but no sample eboot imports either. The engine cannot add imports (cave code can only call imports the module already has, as boot_notice does), and raw syscalls from game code are refused (`SYSTEM_ILLEGAL_FUNCTION_CALL`, §6b2).
- **Where a guard would still add something:** only the two `plt_stub` rules, which force the fallback on every firmware because the native function exists on some consoles but cannot be used there.
  - **`sceAudioOut2Set3DLatency` (`TViD1EZXkNI`), plt_stub ret0 below 10.01.** Today a sub-10.01 cook also skips the call on 10.01+ consoles, which would accept latency 2. Verified on 8.60 (`libSceAudioOut` export `0x28450`): the refusal is pure argument validation (`cmp r14d, 1; ja` and the user-id checks, before the implementation call `0x1d7b0`), followed only by an optional log call. Turning a negative result into 0 is therefore equivalent to today's stub on 6.00–9.60 and keeps the native request on 10.01+. Below 6.00 the GOT pre-fill (`ret0`) applies. Benefit: small (a 3D-audio latency hint on 10.01+ consoles). Risk: low.
  - **`scePsmlMfsrInit` (`3WVD91e12ZQ`), plt_stub `ret:0x8a810012` below 9.00.** It is a plt_stub because the Psml fakelib always provides the export. Today a sub-9.00 cook never runs PSSR, even on a PS5 Pro. Gating the call on the module's own `sceKernelIsTrinityMode` (`tU5e3f9gSiU`; GOT pre-filled `ret0` below 7.01, native from 7.01) would keep base consoles on exactly the native base-console answer and let Pros run the real init. In the 18 sample eboots, every one that imports MfsrInit except GT7 also imports IsTrinityMode (a byte grep of the eboots). Benefit: PSSR on a Pro from a 4.00 cook. Risk: unknown. Psml has its own SDK gates (7.xx/11.00, §6l) and runs with the 4.00 stamp. Only a Pro test can decide it.
- **Engine fit (read in `Patching.cs`).** A guard is an adapter whose import *also* gets the GOT pre-fill. Today `ApplyOne` places adapters with `PlaceChain` (`call_got` = `call [GOT]`) and never pre-fills, while `StubImports` pre-fills only `stub` rules. The new kind combines the two for one NID. The error form is branch-free (so `PlaceChain` may split it across caves). The condition form branches, so it needs `contiguous`, and it needs the condition import's GOT address.
- **Proposed `data/fixes.json` schema (not implemented):**

  ```json
  "TViD1EZXkNI": { "kind": "guarded", "guard": "on_error", "stub": "ret0",
                   "when": "always", "below": "10.01", "proven": false, … }
  "3WVD91e12ZQ": { "kind": "guarded", "guard": "if_import", "condition_nid": "tU5e3f9gSiU",
                   "stub": "ret:0x8a810012", "when": "always", "below": "9.00", "proven": false, … }
  ```

  `stub` serves twice: as the GOT pre-fill (consoles without the export) and as the fallback the guard returns. `on_error` allows only `ret:<value>` stubs (a negative `eax` → the value; out-parameter stubs cannot be emulated after a failed native call). Chain: `sub rsp,8; call [GOT]; add rsp,8; mov ecx,<v>; test eax,eax; cmovs eax,ecx; ret`. `if_import`: save the six argument registers and align, `call [cond GOT]`, restore, `test eax,eax; jz fallback; jmp [GOT]`, then the stub body. When the module does not import `condition_nid`, the rule degrades to today's `plt_stub`, and the report says so. `Knowledge` must reject the new keys outside `guarded` (the safety nets). force_pro keeps lifting MfsrInit (`kind: none`).
- **Console tests needed (testers):** (G1) Yōtei 4.00 cook with the `on_error` Set3DLatency on 8.60: boots like `_3dlatency`. On 13.60 or 10.x/11.x: boots, audio normal. A diagnostic variant with `ud2` on the fallback path should crash on 8.60 and not on 13.60, which proves both branches. (G2) a sub-9.00 cook of a PSSR game with the `if_import` MfsrInit on a PS5 Pro: PSSR available, no crash or corruption. On a base console: same as today. (G3) The pre-fill premise on a physical 4.xx console is already covered by §6s's PPSA18154 boot. An explicit check would be a cook that calls a pre-filled stub at boot (e.g. GetOperationMode, 11.00) on a 4.xx console.
- **Recommendation:** no general guarded mechanism. Keep `stub` as the default "native where present" mechanism and document it as such. Implement `on_error` for Set3DLatency only if the 10.01+ gain is wanted. Implement `if_import` for MfsrInit only once a Pro tester can run G2.
- **Implemented (2026-10-16, user decision): `guarded` with `guard: on_error`, used by Set3DLatency** (now `proven: false`). `if_import` is not implemented. Details, verification (Unicorn emulation, a disassembled AC FW 4.50 cook) and tests: README "Guarded fix kind; Set3DLatency uses it". A Yōtei 4.00 cook for G1 has not been produced yet.

### 6u. Yōtei `0xa0d0c006 GPU_FAULT_BAD_COMMAND_ASYNC` on a physical FW 4.50 console: the store AGC's mode 0 (open, 2026-10-16)

- **Report (user, photo):** a tester's base PS5 on FW 4.50 runs a Yōtei FW 4.00 cook (boot_notice "Backport test files by Arsenic"). It crashes with `0xa0d0c006 (GPU_FAULT_BAD_COMMAND_ASYNC)`, CE-108111-2. The same game works on the user's 13.60 and for other testers. No kernel log or dump. The exact build is not on disk (no `PPSA26344_backport_*` folder remains), but every Yōtei cook since 12 October used store set `4`, whose `libSceAgc` carries the §1.1 patch (`07a995b3…`, mode 0).
- **Where the code comes from:** the kernel's GPU fault path. SceShellCore only names it (§1.1). No GPU microcode or kernel is in any dump (all 46 firmware folders hold user-space libraries; `sys/gpudump.elf` is a dumper, not a decoder), so the GPU side cannot be read. Everything below is user-space evidence.
- **Packet vocabulary does not change (new, static).** Scanner `scratchpad/pm4scan.py` (Capstone sweep of executable segments; 32-bit and both halves of 64-bit immediates shaped like PM4 type-3 headers): FW 4.00, 4.50, 5.02, 7.01, 9.60, 12.00, 12.70, 13.60 `libSceAgc` and the store sets 4, 4.03 and 9.60 all emit the same 43 opcodes with the same count fields. The newer AgcDriver adds header `0xc0079300` (opcode 0x93) plus a NOP, but FW 4.50's own Agc already emits `0xc0079300`. Yōtei's eboot builds **no** packets inline (6 false positives), so every packet goes through AGC calls. A 4.50 console therefore never sees an unknown opcode from these libraries. What differs is packet **content**.
- **Yōtei hits the FW 4.xx AcquireMem workaround condition (new, static).** GCR is the 4th argument of `sceAgcDcbAcquireMem` (`ecx`) and the 2nd of `sceAgcAcbAcquireMem` (`esi`); FW 4.50 Agc `0x2eb0`/`0x1f0`. Mode 1 splits the packet when `(gcr & 0x108) == 0x108 && (gcr & 0x2a0)`. Yōtei has 51 call sites (`scratchpad/acqsites.py`). The constant sites pass 0x300, 0x380, 0x280, 0x9000, 0xd000, 0x9288 and 0x19288 (bit 3 without GLV_INV), plus 0x20 and 1 in other registers, and none qualifies. The full-range barrier helper (`0x172e60d…0x172e6c7`, Dcb, base 0x100/size −1) only produces 0x1/0x20/0x80/0x100/0x200/0x8000/0xc000, the same set §6s found in Tomb Raider. **The ranged compute barrier at `0x172ea6c…0x172eae9` (`sceAgcAcbAcquireMem`) builds `(f&1 ? 0x108 : 0) | (f&0x10 ? 0x208 : 0) | (f&2)<<6 | … | 0x1000`**, which is GLV_INV with GL1_RANGE bit 3 together with GL1_INV/GLK_INV/GLM_INV: exactly what FW 4.00–4.51 Sony Agc always splits. The helper's marker (`and edi, 0x208`) also occurs in Dying Light: The Beast and AC Black Flag; no other sample has it.
- **12.70 AGC modes (store set 4, unpatched `eace8ac1…`, init `0x8bf6…0x8c26`):** `mode = (selector 0x52 ? 2 : 1)`, then 0 if selector 0x53 is set or the SDK major is not 4, plus 4 × selector 0x70. Dcb `0x3896` and Acb `0x22c`: bit 0 (mode 1) adds the GLV-only ACQUIRE_MEM (64 bytes). Bit 1 (mode 2) only clears GL1_RANGE (`and ecx, 0xfffffff3`) when GLV_INV and range bit 3 are both set, with no size change. The §1.1 patch forces mode 0 for every cook on every console.
- **Console evidence by AGC mode:** every community 4xx+ build that ran on a 4.xx console shipped an *unpatched* AGC and therefore mode 1 under the SDK-4 stamp: Hades II on FW 4.03 (set-4.03 build `e1c8f6dc…`), GT7 and Dying Light (`eace8ac1…`). Our mode-0 cooks: Tomb Raider on 4.50 boots with corruption but never emits the combination (§6s); Yōtei on 4.50 emits it and faults. DW3 on 13.60 faulted with mode 1 (§1.1) and works with mode 0.
- **Conclusion (strong static evidence, not console-confirmed):** a FW 4.00 cook running AGC mode 0 sends FW 4.xx consoles an ACQUIRE_MEM form that Sony never sends them. The FW 4.xx system Agc splits it for every title, and from 5.02 Sony stops splitting for titles with SDK above 4. That fits "4.50 faults, 13.60 and other testers do not". It is neither a pure game bug nor a pure library bug: the game's ranged compute barrier meets the encoding our patched AGC chooses and the 4.xx GPU firmware's limits. Mode 1 is wrong in the other direction (DW3 on 13.60).
- **Candidate fix (not implemented): AGC mode 2 for every cook.** It is Sony's own per-title alternative on FW 4.xx (selector 0x52 in the 4.50 Agc). It keeps the 32-byte packet (no GetSize/size hazard). On 5.02+ the only change is full-range GL1 invalidation where a range was requested, a superset of the requested work. Patch idea: 3 bytes at `0x8c23` that load 2 (e.g. `6a 02 58`, `push 2; pop rax`) instead of `mov eax, esi; nop`, in sets 4 and 4.03 (check the same VA in the 9.60 and 10/ppsa34008 builds).

(U2) Yōtei 4.00 cook with a mode-2 AGC on 4.50, 8.60 and 13.60. (U3) DW3 FW 4 cook with mode 2 on 13.60 (must still boot and save). (U4) optionally Yōtei with the unpatched AGC (mode 1) on 4.50, which should also boot if the hypothesis holds.
- **Implemented as an opt-in (2026-10-16, user decision):** store variants `fakelibs/4/agc_mode2` (`9ec2512f…`) and `fakelibs/4.03/agc_mode2` (`6917fbc8…`), selected by the new option `agc_mode2` (group Libraries, probe `console`). Tests: `AgcModeTests` (option, and a 3-byte-only diff against the base for both sets); `ProbeTests` lists it as a console-choice probe. Cook goldens gain one `probe console-choice agc_mode2` line each.
- **U2 build `D:\PS5\BackportTests\PPSA26344 - Ghost of Yotei v02.002.000\PPSA26344_backport_4.00_agcmode2`** (CLI, source `PPSA26344-app0` v02.002.000, target 4, `--patch-param --candidate-fixes`, options `save_prepare_compat audio_port_compat auto_pro psml_kpn9 agc_mode2 boot_notice`, toast "Backport test files by Arsenic - AGC mode 2"). eboot `f5b67d1f…`, libc `0513b147…` (same as `_waitfix`), Agc `9ec2512f…`, AgcDriver `43153558…`, Psml `1a3727fd…` (psml_kpn9), Ampr `82484486…`, PlayGo `a0f20f40…`, param requires `0x04…`, and `ampr_emu.index` (105,812 entries, 9 from the overlay; built with `AmprIndex.Build` from that exact source folder). ### 6v. Review of the Decker97 backport tool (`E:\PS5_TOOLS\Decker97`, "PS5 Backport GUI by Deckerr97" 0.2.0-beta) (2026-10-17)

Source: the PyInstaller bundle's engine (`backend.zip`; 155 modules compiled as marshal `.pyb`, disassembled with Python 3.14 without running them), its data (`known_compatibility_patterns.json`, `compatibility_family_registry_v2.json` 2.4.4, policies) and 18 zips that its code calls "user-confirmed WORKING" packages. - **Store fakelibs answer "not Pro" on every console (verified, static).** In store sets 4, 4.03 and 9.60 (and `10/ppsa34008`), `libSceAgc` defines `sceKernelIsTrinityMode` locally (symbol `tU5e3f9gSiU#E#F`, `st_shndx` ≠ 0, VA `0x26e3` = `xor eax,eax; ret` carved from existing code), and `libSceAgcDriver` defines `sceKernelHasTrinityMode` locally (VA `0x450` = `xor eax,eax; ret`; PLT `0xb890` patched to `jmp 0x450`). Native 12.70 Agc/AgcDriver import both from libkernel, and so does our set 7. Our own `--define-symbol` mode produces the same form. The loader therefore never binds the native functions. Set 4's `sceAgcGetIsTrinityMode` (byte-identical to native 12.70 at `0x99f0`) calls the local zero, and the fakelib Agc is the module that exports it to the game. **So `auto_pro`'s warning ("sceAgcGetIsTrinityMode native from 9.00; a Pro on those firmwares is detected") does not hold when a store Agc is loaded, and the store breaks its own rule "Replacement libraries must report the actual console correctly."** The local symbols are not exported to other modules: the only export library is `libSceAgc`, so the game's own libkernel import is not shadowed.
- **Store Psml cannot start PSSR on any console (verified, static).** Set 4 `libScePsml` `72855f03` (also `10/`, `11/`) and the `psml_kpn9` variant `1a3727fd` are native 13.60 Psml (build J03950001, same size) plus an SDK retag and 27 imports rewritten into local definitions. Those are `sceKernelIsTrinityMode` → ret 0, `sceKernelGetOperationMode` → `*mode = 0, *lowEnergy = 0`, `sceKernelGetAppInfo2`, `sceKernelTitleWorkaroundIsEnabled2`, two VideoOut calls, and **libc++ `_Mtx_init/lock/unlock/destroy`, throws and locale helpers → ret 0** (no locking even on firmwares that export them). The Psml one-time init (`0x2bfb4`) stores `IsTrinityMode() != 0` in a flag. Both `scePsmlMfsrInit` (`0x2c226`) and `scePsmlMfsr2Init` (`0x9edd`) read it and fail with "MFSR2 isn't supported in sceKernelIsTrinityMode() == 0". With these files PSSR v1 and v2 never initialise, even on a Pro with `force_pro` + `psml_kpn9`. Set 4.03 Psml `6632020e` has the same local IsTrinityMode. The 9.60 sets' Psml (`cfe210a3`, `e09e5c27`) keep Sony's imports for IsTrinityMode and the mutexes, but their `sceKernelGetOperationMode` PLT jumps straight to the same `*mode = 0` stub (found by `StoreImportFormTests`; fixed with the rest).
- **Fix path (feasibility verified, not console-tested):** rebuild these libraries from the native dumps (12.70 Agc/AgcDriver, 13.60 `system_dec` Psml) with Studio's normal loader-overridable GOT pre-fills instead of local definitions. `ps5backport stub <native 13.60 Psml> OUT --unknown --firmware 4.00` (scratch run) leaves `sceKernelIsTrinityMode` and `_Mtx_lock` as imports (`st_shndx 0`) with a GOT pre-fill, and applies the `opmode_normal` rule to GetOperationMode. Below 7.00 the answers stay "base"; from 7.00 the console's own functions answer. Decker97 needed the same change for its only hardware-proved base+Pro Pro-stack package (Black Flag V16, base FW 4.50 + Pro FW 13.60: "AGC symbol 288 → UNDEF HasTrinityMode" plus a return-0 GOT seed). Open question: Decker97 routes the eboot through `sceKernelHasTrinityMode` (SoC check only) because `IsTrinityMode` also needs the per-process sysctl `kern.gjevmtrb`. Whether that sysctl is set for an SDK-4-stamped process on a Pro is unknown; only a Pro test can tell.
- **Rebuild installed in the store (2026-10-17, user decision; not console-tested; `fakelibs/README.md`, test `StoreImportFormTests`, originals in `work/fakelib-backups/native-imports-2026-10-17/`):** `work/fakelib-native-imports-2026-10-17/` (the patcher `undefine_imports.py`, `install_staged.py`, the signed files, `SHA256SUMS.txt`). Scope: `sceKernelIsTrinityMode` (Agc), `sceKernelHasTrinityMode` (AgcDriver), and for Psml `sceKernelIsTrinityMode`, `sceKernelGetOperationMode` and libc++ `_Mtx_init/destroy/lock/unlock`. #### Mid-level "progress automatically saved" icon is a meta save, not a run checkpoint (2026-10-12)

Static analysis of the original Il2CppUserAssemblies (metadata v31 parsed directly; method addresses reproduce the ones above, e.g. SaveRun `0x8c51b0`). The FW 4 cook changes only the SKU byte at `0xf4ae2a`, the two popup bytes, the SDK fields and the code extension in this module; no save code differs from the original.

- **Run state is written only at level exits.** Direct callers of `GameplaySaveManager.SaveRun` (`0x8c51b0`) are `TransitionStackElement.SaveRun` and three debug/state-select tools. The only data reference to SaveRun is its IL2CPP method-pointer entry, so there is no hidden delegate path.
- **The mid-level flame comes from `SavePersistent` (`0x8c5690`).** Its callers include `SavePersistentFeature.OnStart`, `ForceSavePersistentEffectData`, `ArchivistService.ClaimReward`, skill tree, forge, altar, collection and skins UIs. SavePersistent calls `Save` with an exclude list containing only `PlayerSaveData`. Meta, quest and global sections are saved; player run state is not. Ubisoft profile writes show the same icon (`SaveHintUI` ops 0/1/3/4).
- **Run-save freshness rule.** `RunSaveExists` → `RunSaveExistsAndIsFresh` (`0x8ce520`) loads both files and compares `FindSaveSection<GlobalSaveDataSection>().totalRunsRealPlaytime` (double, +0x20). The run save is used only if its value is greater than the persistent file's. If the persistent file cannot be loaded or has no global section, the run save counts as fresh. `GlobalSaver.OnSaveRequested` (`0x7e44a0`) copies `PlaytimeService.totalRunsRealPlaytime` (+0x38), which `PlaytimeService.Update` (`0x872180`) increases every frame. A persistent save written after the last level-exit save can therefore make that run save stale. This is retail logic.
- **Conclusion.** Resuming from the start of the level after a mid-level quit is the game's design, not a backport save failure. A developer reply from the Early Access period ([Steam](https://steamcommunity.com/app/2717880/discussions/0/4335356530803351458)) describes the same behaviour. No rule or option should change this: forcing SaveRun mid-level would be a per-game gameplay patch the game's load path does not support. Console check if needed: run the original game on 13.60 with the same mid-level quit; it should behave identically.

- The old allocator (`0xd0`) uses a 256-MiB internal pool; the newer allocator (`0x3a0`) uses 64 MiB. Both use 16-KiB alignment and a 512-entry chunk table. Exact old provenance and relative runtime suitability remain unknown.
- The old AMM command-buffer constructor/destructor (`0x1b640/0x1b650`) only return zero. The new counterparts (`0x20a80/0x20d10`) register/unregister command-buffer lifetime in a side table, matching imported source. Registration entered upstream in c343e32. Preserve newer behavior absent an observed regression.
- The new binary uses Multiple/Requests AIO imports versus the old single-request APIs; upstream 56ecc32 (0.3.6.4) introduced batch submission in the reactor. Added event/wait/join/time-counter imports demonstrate implementation changes, not executed runtime paths.
- `sceAmprAmmSubmitCommandBuffer` (`0x1cfa0` vs `0x22830`) has the same normalized 39-instruction body. Completion-wait wrappers also retain the same forwarding behavior.
- Against exact FW 4.03 metadata, old/new published binaries respectively resolve 98/112 function imports, plus one data import each, with no missing/unknown functions. The source-rebuilt module resolves 111 function imports with no data imports, missing or unknown functions.
- The 38-reference mandatory-hook matrix covers FW 4.00–12.70 entries, with 48 mandatory hook entries and no absent NID exports in each reference. This is export presence, not ABI/hook-runtime certification.
- Payload verification completed with `exports=118`, `definitions=122`, `imports=111`, `libc_internal_imports=9`, `kernel_imports=102`, `hash_buckets=234`, `hash_changed_bytes=231`, `fself_version=0x02000001`; required libraries were libSceLibcInternal.prx and libkernel.prx.

No conclusion that a larger pool or fewer imports is universally better is supported. Static reference/export checks do not prove console ABI, data-import behavior or complete runtime compatibility.

### 5. Performance, UI, decoder and architecture evaluations

Surviving reports: `../README.md#performance`, `../README.md#diagnostics-and-ui`, `../README.md#instruction-decoder`, `../README.md#cli-catalog-schema-decisions`, `../README.md#verification`.

Accepted performance changes were one firmware metadata parse per run and signing directly from existing ELF memory slices. Before/after payload and normalized legacy report hashes matched for the documented paired workloads. The accepted changes reduced public large Cook allocation 579.6 → 387.6 MiB (~33%) and private large Cook allocation 2,398.0 → 1,974.1 MiB (~18%). Private analyses saved about 109 MiB per operation. Private small Analyze nevertheless had higher measured working-set/LOH peaks, so reduced allocation is not a universal peak-RAM or leak-free claim.

Focused metadata benchmark: duplicate loads 218.52 MiB / 236.2 ms versus one load 109.93 MiB / 124.9 ms. Small sample counts and wide timing intervals prevent precise speed guarantees. The private large Cook still reached approximately 1.8–1.9 GiB working set. Two-pass loading, ArrayPool, scratch ELF files, Channels and parallel transformations were deferred because of measured tradeoffs and unproven full-pipeline equivalence.

UI filtering experiment on 10,000 rows: showing the full result dropped from 10,001 collection notifications to 1, approximately 2.72 MB allocated to 82 KB, and roughly 16–17 ms to 0.7–1.5 ms in recorded runs. This is a focused view-model measurement, not an interactive latency/accessibility proof. Headless and native process memory do not isolate every Skia/GPU allocation or demonstrate a long-running leak-free UI.

Decoder evaluation passed 530 specified synthetic reference cases (18 named plus 512 generated), and decoded 8 named stub bodies plus 45 adapter blocks without invalid/truncated instructions. Linear segment decoding avoids some byte-pattern false positives but can lose alignment after embedded data and miss real code. Existing eboot counts differed by two sites. Iced 1.21.0 stays an optional evaluation dependency; replacing the production scanner was rejected. No reference count establishes runtime reachability or complete ABI safety.

Phase 8 retained the existing CLI parser and JSON catalog. The SQLite experiment checked semantic round-trip and equal query hits, not persisted .NET provider/crash/concurrent-write behavior. 43,000 membership queries took about 6.3–7.0 ms with JSON sets versus 51.8–64.8 ms with per-query in-memory SQLite calls; this does not justify a production migration. The prototype schema validated 52 existing fix records and 6 edge cases. A copied-record `proovn` typo was rejected by the schema but accepted/defaulted to Proven=true by the then-current Core; no such typo was found in repository data. Unknown stub references and empty adapters still require Core semantic validation. Mandatory/versioned full schemas remain an authoring-contract decision, not a completed runtime feature.

Mutation evaluation of Firmware.cs recorded 20 killed, 3 survived, 0 uncovered and 0 timeouts, with 4 compile-error and 2 ignored target mutants. The survivors were redundant input checks whose removal still rejected malformed inputs downstream. This scoped experiment is not a whole-engine mutation score.
